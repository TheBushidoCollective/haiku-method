Field notes · 2026-05-19

Two harnesses, one shape.

Anthropic published a post on harness design for long-running agent apps. We've been building one for about a month. Most of it is the same picture. The places we diverge are the interesting part.

The eerie thing about reading it was how much of the architecture we'd already converged on independently, in a different vocabulary. They say planner / generator / evaluator; we say hats in a plan → do → verify sequence. They say agents communicate via files; our whole substrate is files. They say contract negotiation before implementation; we shipped a pre-execute spec review walk yesterday.

Different teams, same problems, similar answers. That's the useful read.

A side-by-side of Anthropic's harness design and the H·AI·K·U engine, with two concrete suggestions for what we should do next.

§ 1 — The convergenceWhere we landed in the same place

Seven patterns from their post that map cleanly onto something we already have:

Match Multi-agent specialization

Anthropic
Distinct personas: planner, generator, evaluator. Each addresses a specific failure mode, and the separation enables better error detection.
H·AI·K·U
Hats in a plan → do → verify sequence (ARCHITECTURE.md §3). Every stage ends in a verifier; adversarial review agents fire externally. Same shape, different vocabulary.

Match State handoff through files

Anthropic
"One agent would write a file, another agent would read it and respond either within that file or with a new file." Decouples agents, enables clean session boundaries.
H·AI·K·U
This is our whole substrate. .haiku/intents/<slug>/units/*.md, feedback/FB-NN.md, intent.md. We went further: v4 dropped state.json and made outputs-on-disk the only signal the cursor reads.

Match Context reset over compaction

Anthropic
"Context resets — clearing the context window entirely and starting a fresh agent, combined with a structured handoff — address both compaction's drift and context anxiety."
H·AI·K·U
Every hat fires as a fresh subagent through Task with a structured mandate. The orchestrator is the persistent thread; each hat starts cold with only the artifacts it needs.

Match External evaluation, not self-eval

Anthropic
"When asked to evaluate work they've produced, agents tend to respond by confidently praising the work — even when, to a human observer, the quality is obviously mediocre."
H·AI·K·U
Adversarial review agents, spec-conformance gate, intent-completion review agents. The feedback-assessor is a terminal hat that independently decides closure. Verifier ≠ author by construction.

Match Contract negotiation before implementation

Anthropic
"The generator proposed what it would build and how success would be verified, and the evaluator reviewed that proposal to make sure the generator was building the right thing."
H·AI·K·U
Our pre-execute dispatch_review walk. Engine roles (spec, continuity, cross-stage-consistency) audit the planned spec before any wave-ready hat dispatch. Independent convergence on the same idea.

Match Active runtime validation

Anthropic
Evaluator drives the live app through Playwright MCP — navigates, screenshots, asserts. Catches runtime issues invisible in static review.
H·AI·K·U
The haiku_view MCP tool returns a URL (boot mode for runnable apps via the project's dev script on an ephemeral port; viewer mode for static artifacts via the SPA artifact-browser with mime dispatch + specialized viewers for KiCanvas, Tracespace, <model-viewer>, tscircuit). Per-studio runtime-verifier.md review-agent mandates hand the URL to the bundled headless Playwright MCP, drive the declared flows, save proof PNGs to [intent]/[stages/<stage>/]proof/*.png. Studios can ship their own contributed React app for richer rendering — hwdev's multi-pane Board Explorer is the canonical example.

Match Log-driven prompt tuning

Anthropic
Methodology is "read logs, identify divergence from expectation, adjust the agent's prompt, run again." Sustained signal turns into structured revisions.
H·AI·K·U
Default-on reflection loop. At each stage close the agent writes stages/<stage>/observations.md capturing out-of-band churn (mandate ambiguity, engine friction, surprise) that artifacts on disk don't already show. At intent close a record_reflection pass reads every observations.md + the full FB stream + iterations/outputs and produces three outputs in one autotune:-prefixed commit: (1) a synthesized reflection.md at the intent root, (2) project-local overlays written directly under .haiku/... for findings the cascade can fix today (no FB queue, no separate review surface — the PR is the human gate), and (3) haiku_report calls with the stable [autotune engine-class] prefix for findings the cascade can't fix (engine code, cursor logic, validator boundaries — the report routes to the H·AI·K·U team via the existing Sentry pipeline). Engine prompts live on disk at plugin/prompts/ with a two-tier cascade (.haiku/prompts/ wins over plugin/prompts/) so overlays land without a rebuild. Opt-out via reflection: false on intent FM.

Seven for seven on the load-bearing patterns. Different vocabularies, same shapes. That's the validation.

§ 2 — The divergenceWhere we go different directions

Diverge How much to decompose

Their warning: don't over-specify at planning, because lock-in errors cascade. Their evaluator stays "focused on product context and high-level technical design rather than detailed technical implementation."

We go the other way. The elaborate phase fans out subagents per discovery template, produces unit specs with depends_on DAGs, executable quality_gates, criteria-with-verify-commands. We've been burned by both modes — drift when specs are too loose, lock-in when they're too tight. Worth a real conversation about whether some of our elaborate-phase rigor is scaffolding the model no longer needs.

Diverge Removing scaffolding as models improve

Their Opus 4.5 → 4.6 lesson: "Every component encodes an assumption about what the model can't do on its own. Stress-test those assumptions, because they may be incorrect and they can quickly go stale as models improve."

The lesson is real for us, but the wrong place to apply it is the hat list. Our per-stage and per-intent loops are minimal — distill, review-against-knowledge, execute (plan → do → verify), review-units-as-whole, human-review, advance. Each layer is structurally distinct work; none is removable without losing coverage. Where scaffolding actually accumulates is inside the hats — verbose anti-pattern lists in mandate md files, defensive engine-side validators against failure modes that no longer happen on current models, overlapping review-agent lenses, fanned-out discovery templates that could be one pass. The reflection loop is wired to surface exactly this signal at intent close — write overlays for cascade-fixable findings, ship engine-class friction via haiku_report — but it has not yet fired on a real intent. A manual audit pass we ran against the engine's own prompts (the two-tenant test — "enough to act accurately, not so much that the agent skips ahead") trimmed seven of the longest mandates and cut a redundant gate block, with all 1,673 tests still green. That was hand-driven; the loop existed but we didn't use it. The pipe exists; nobody's pulled water through it yet.

§ 3 — Our edgesWhat we have that their post doesn't address

Ours One instruction at a time

Their post is candid: "But some problems remained persistent. For more complex tasks, the agent still tends to go off the rails over time." They name two failure modes — context-window fill plus context anxiety, and self-evaluation bias — and they patch each one. Context resets fix the first. Separating the evaluator from the generator fixes the second. Both are real fixes, both add "orchestration complexity, token overhead, and latency," and both leave the underlying shape intact: a single agent running an open-ended loop, deciding its own next move, sometimes for a very long time.

We never gave the agent that loop. haiku_run_next reads disk, walks the cursor, and returns exactly one structured action — start_unit_hat, dispatch_review, advance_phase, file_feedback, seal_intent. The agent's job is to execute that one action and call haiku_run_next again. There is no "what should I do next?" question for the agent to answer; the cursor answers it from on-disk state every time. Each hat fires as a fresh subagent through Task with a structured mandate, terminates, and the parent agent reaps the return and re-ticks.

This collapses both of their persistent failure modes structurally rather than as patches. Context fill can't compound because the agent doing the work has a one-turn horizon — there is no lengthy task from the agent's perspective, only from the cursor's. Context anxiety has nothing to wrap up prematurely from, because the agent isn't running a long task it could decide to cut short. Self-evaluation drift can't happen because the verifier is a different hat fired in a different subagent with a different mandate; the design forbids the same context from authoring and grading. Anthropic's patches address symptoms downstream of "agent decides its own next move." Take that decision away from the agent and the symptoms don't arise.

This is also what makes our context-reset story load-bearing rather than ornamental. The cursor is the persistent thread; the on-disk artifacts are the memory; every agent invocation starts cold with exactly the information it needs for one move. It looks like Anthropic's reset model from the outside, but it's the design's default state, not a recovery move.

Ours Drift gate / premise-witness model

A runtime check that the agent's premise still matches reality before each tick. They don't discuss this at all. Long-running agents drift; ours notice.

Ours Forward-only lifecycle

Completed units are never re-edited. Corrective work goes through new units authored from upstream elaborate — the FB-as-unit fix loop. They describe agents revising files; we treat units as immutable once verified, with feedback as the only way back. Different stance, deliberately.

Ours MCP-as-contract boundary

Workflow-managed files are guarded by a PreToolUse hook — agents go through MCP tools or get rejected with a redirect message. Their agents communicate through files but they don't describe a hard enforcement layer around who can edit what. We do, and the engine relies on it for invariants like "stage branch is always ahead of main."

Ours Cascade resolution for mandates

Hats and review agents resolve through a three-tier cascade: stage → studio → global, first hit wins, with project .haiku/ overriding plugin at each tier. Lets us share defaults and override locally without forking. Their setup looks flat per-task.

§ 4 — What we should doOne suggestion, the one that actually matters

Reading their post against ours, one open work item stands out — and it's the one whose absence the whole "field notes" framing keeps circling back to.

Fire the reflection loop on a real intent. Then on the next four.

Why: The loop is wired. The cursor emits record_observations at each stage close. It emits record_reflection at intent close. The prompt template tells the agent to land overlays under .haiku/... and ship engine-class findings through haiku_report with the stable [autotune engine-class] prefix. None of that has ever actually run end-to-end. No observations.md exists on disk. No reflection.md exists. No autotune:-prefixed commit has landed. The shape of the loop is theoretical until it's fired against signal from a real run; until then we don't know whether the prose in the prompt produces a useful synthesis or a fluffy one, whether the overlay diffs are too narrow or too sweeping, whether the engine-class report shape lands well in Sentry. How: ship the next intent end-to-end with reflection: true (the default), read the observations.md files as they land, read the reflection.md at close, read the autotune: commit's diff. Calibrate the prompt body against what it actually produced. Then do it four more times before deciding whether the discipline is "accept trims, reject additions" or something else entirely. Without that first run there's nothing to be disciplined about.

The convergence is reassuring — two teams chasing the same problem landed on the same shape, seven patterns over. The interesting gap isn't where we converged; it's where we made a different bet at the foundation. Anthropic's persistent failure modes — context drift on lengthy tasks, self-evaluation bias — are problems for any harness whose agent runs an open-ended loop. Patches help. But "the agent decides what to do next" is the seed those failure modes grow from, and we never planted it. The cursor decides; the agent executes one step. The drift gate, the forward-only lifecycle, the MCP-contract boundary, the cascade resolution — they each follow from that one choice.

The pipe exists. The harder thing is pulling water through it.
